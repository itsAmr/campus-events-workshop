# Part 0 — Design the database

**Time:** 15 minutes  
**Goal:** design the table that stores RSVPs, so the database itself guarantees the rules that must never break.

The `events` table already exists in `api/migrations/001_init.sql`. You will add the `rsvps` table next to it.

## Discuss: what could go wrong?

Your facilitator will show three ways to store RSVPs. For each one, ask: what happens when someone cancels, RSVPs twice, or an event is deleted?

1. An `rsvp_emails` column on `events` holding `"martlet@mcgill.ca,stinger@concordia.ca"`.
2. An `rsvp_count` column on `events` that the code adds 1 to on every RSVP.
3. A separate `rsvps` table with `event_id` and `email` columns and no other rules.

<details>
<summary>Discussion notes</summary>

1. Cancelling means editing text inside a string, and finding "every event Martlet is going to" means searching every event's string. One fact belongs in one row.
2. The count says how many, but not who. Nothing stops a double RSVP, and the number drifts the first time a bug or crash skips an update. Store the RSVPs and count them when needed.
3. This is the right shape, but nothing stops the same email signing up twice or an RSVP pointing at an event that no longer exists. The rules are missing.

</details>

## 0.1 Design the `rsvps` table

Open `api/migrations/001_init.sql` and find `TODO(part-0.1)`. The rest of the app reads these exact columns, so keep the names:

| Column | Holds |
| --- | --- |
| `id` | a number for each RSVP, generated by the database |
| `event_id` | which event the RSVP is for |
| `email` | who is coming |
| `created_at` | when they RSVP'd, filled in by the database |

How you enforce these rules is up to you:

1. Every RSVP belongs to an event that exists.
2. One RSVP per email per event. The same email can RSVP to many different events.
3. Deleting an event deletes its RSVPs.
4. An RSVP always has an email.

Keywords worth looking up: `PRIMARY KEY`, `AUTOINCREMENT`, `NOT NULL`, `DEFAULT`, `FOREIGN KEY ... REFERENCES`, `ON DELETE CASCADE`, and `UNIQUE (...)`. The `events` table above uses several of them. Copy its `created_at` line so every timestamp in the database uses the same UTC format.

Check your design. Each test is one rule:

```bash
npm run check:0
```

Read the list of ✓ and × at the top: each × is a rule your table doesn't enforce yet, with a hint underneath. Everything after that list is detail for when the hint isn't enough, and the `npm error` lines at the end only mean "a test failed".

Then rebuild your local database so it has the new table:

```bash
npm run db:reset
```

The database records which migration files it has already run, so it never runs `001_init.sql` twice. Editing an old migration only works here because your local database is disposable. A real project adds a new migration file instead, as you will see in Part 2.

## Watch the database say no

Open a SQL prompt on your local database:

```bash
npm run db:shell
```

Run one statement per line:

```sql
SELECT id, title, capacity FROM events WHERE title LIKE '%Climate%';
SELECT * FROM rsvps;
INSERT INTO rsvps (event_id, email) VALUES (25, 'martlet@mcgill.ca');
INSERT INTO rsvps (event_id, email) VALUES (999, 'you@mcgill.ca');
```

If the first query shows a different `id`, use that number instead of `25`. The third statement should fail with a `UNIQUE` error and the fourth with a `FOREIGN KEY` error. Type `.exit` to leave.

Think about it: the API already checks for a duplicate RSVP before inserting one, so it can reply with a friendly `409 Conflict`. Why keep the `UNIQUE` rule too? (Hint: two requests arriving at the same moment, or a program like this shell that writes without going through the API.)

Stretch: should `Martlet@McGill.ca` and `martlet@mcgill.ca` count as the same person? Look up `COLLATE NOCASE`.
